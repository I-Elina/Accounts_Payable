📋 Section 1: Complete Rule Catalogue (R01 to R11)

The decision engine runs in two deterministic passes. Hard violations always route an invoice straight to Exception regardless of score. Soft violations decrement the confidence score.

Rule ID Exception Type Severity Penalty Pass Trigger Logic & Conditions
R01 missing_field Hard 0.50 Pass 1 Any required field is empty or whitespace: invoice_number, vendor_name, invoice_date, total_amount.
R02 invalid_amount Hard 0.60 Pass 1 total_amount is unparseable text, negative (< 0), or zero (≤ 0).
R03 invalid_date Hard 0.40 Pass 1 invoice_date cannot be parsed as a valid calendar date (e.g., "31/31/2026", "invalid").
R04 future_date Soft 0.30 Pass 1 invoice_date is strictly greater than as_of_date (default: today UTC; fixed date for tests: 2026-10-01).
R05 calculation_mismatch Soft 0.35 Pass 1 Both subtotal and tax_amount are present, and |subtotal + tax - total| / total * 100 > 0.5%.
R06 exact_duplicate Hard 0.80 Pass 1 Identical normalized tuple (vendor, invoice_number, total) found in an earlier invoice in the batch or upload history.
R07 policy_limit Soft 0.20 Pass 1 total_amount > policy_limit (default threshold: 100,000 INR).
R08 unknown_vendor Soft 0.20 Pass 1 Normalized vendor not present in vendor_master.csv, or category not in approved contract list.
R09 fuzzy_duplicate Soft 0.35 / 0.20 Pass 2 Gate check: invoice_number ratio ≥ 0.80. Weighted similarity: 35% Vendor + 30% Number + 20% Amount + 15% Date. Fires 0.35 if score ≥ 0.85; 0.20 if 0.70–0.85.
R10 fuzzy_duplicate Soft 0.15 Pass 2 Fires only if R09 triggered AND amount_difference_pct ≤ 1.0% against the matched record.
R11 amount_outlier Soft 0.20 Pass 2 Vendor historical standard score: Z = (total - mean) / std > 3.0 (requires ≥ 5 historical invoices for that vendor).

🎯 Section 2: Confidence Scoring & Decision Routing

Every invoice receives a calculated confidence score between 0.00 and 1.00:

confidence = round(max(0.0, 1.0 - sum(violation.penalty for violation in violations)), 2)
Routing Decision Rules:
  • Rule 1 (Hard Rule Override): Any hard violation (R01, R02, R03, R06) automatically routes the decision to Exception.
  • Rule 2 (Auto-Pass Band): If no hard violations and confidence ≥ auto_pass_threshold (0.85) → Auto-passed. (Review status: not_required).
  • Rule 3 (Needs Review Band): If 0.40 ≤ confidence < 0.85 → Needs review. (Review status: pending).
  • Rule 4 (Exception Band): If confidence < 0.40 → Exception. (Review status: pending).

🧪 Section 3: Step-by-Step QA Test Runbook

Follow these steps to thoroughly test the live backend API. All commands can be run via Terminal/PowerShell or directly in Swagger UI at http://localhost:8000/docs.

Test 1: Healthcheck & Service Liveness GET /api/health

Verify that the service is running and report current AI configuration mode.

curl -s http://localhost:8000/api/health

Expected Response (200 OK):

{
  "status": "ok",
  "ai_mode": "mock"
}
Test 2: Database Seeding & Ingestion Pipeline CLI: python -m backend.seed

Initializes the SQLite schema and runs process_upload on the demo dataset (1,000 invoices).

python -m backend.seed

Expected Output:

Initializing database...
Seed complete! Upload ID: 1, Processed: 1000 rows.
Auto-pass: 816, Needs review: 90, Exception: 94
Test 3: Querying Invoices with Multi-Filters GET /api/invoices

Test filtering by decision and sorting by confidence ascending (lowest confidence first).

curl -s "http://localhost:8000/api/invoices?decision=needs_review,exception&sort=confidence&order=asc&page=1&page_size=5"

Verification Checklist:

  • HTTP 200 OK with paginated structure: items, total, page, page_size.
  • Every item contains only canonical snake_case fields.
  • Confidences appear in ascending order (e.g. 0.20, 0.40, 0.50).
Test 4: Invoice Detail & Matched Record Inspection GET /api/invoices/{id}

Retrieve full invoice detail for fuzzy duplicate showcase INV-1042.

curl -s "http://localhost:8000/api/invoices/2"

Verification Checklist:

  • matched_record contains "INV-0987".
  • matched_invoice contains the full canonical details of earlier invoice INV-0987.
  • violations array contains structured evidence with vendor_similarity and amount_difference_pct.
Test 5: On-Demand AI Summary Generation POST /api/invoices/{id}/summary

Requests plain-English explanation for a flagged invoice. Checks anti-hallucination validation.

curl -s -X POST "http://localhost:8000/api/invoices/2/summary"

Expected Response (200 OK):

{
  "ai_summary": "Invoice INV-1042 appears to duplicate INV-0987. Probable duplicate of INV-0987 (96% similar)...",
  "ai_suggested_action": "investigate",
  "ai_summary_status": "ready"
}

Check audit trail: GET /api/audit?invoice_id=INV-1042 must contain an AI_SUMMARY_GENERATED event!

Test 6: Human Review & 409 Conflict Protection POST /api/invoices/{id}/review

Approve pending invoice, then verify that re-reviewing returns HTTP 409 Conflict.

# 1. First review: Approve
curl -s -X POST "http://localhost:8000/api/invoices/2/review" \
  -H "Content-Type: application/json" \
  -d '{"action": "approve", "reviewer": "Shree", "comment": "Verified with vendor"}'

# 2. Second review: Must fail with 409 Conflict
curl -s -X POST "http://localhost:8000/api/invoices/2/review" \
  -H "Content-Type: application/json" \
  -d '{"action": "reject", "reviewer": "Alex"}'

Expected 409 Response:

{
  "error": {
    "code": "CONFLICT",
    "message": "Invoice INV-1042 cannot be reviewed because its current review status is 'approved'",
    "details": ["review_status must be 'pending', currently 'approved'"]
  }
}
Test 7: Chat Assistant & Review Proposal Safety POST /api/chat

Ask the chatbot to approve an invoice. Verify that the assistant only proposes the action and never changes the database row.

curl -s -X POST "http://localhost:8000/api/chat" \
  -H "Content-Type: application/json" \
  -d '{"message": "Approve INV-1042"}'

Verification Checklist:

  • Returns a proposal object: {"type": "review_proposal", "invoice_id": "INV-1042", "action": "approve"}.
  • Inspect GET /api/invoices/2 → review status remains unchanged!
  • Inspect GET /api/audit → no REVIEW_APPROVED audit record was created!
Test 8: Formula-Safe CSV Report Download GET /api/uploads/1/report

Download the short exception report. Verify encoding and spreadsheet formula injection protection.

curl -s -O -J "http://localhost:8000/api/uploads/1/report"

Verification Checklist:

  • Filename header: ap_exception_report_1.csv.
  • Starts with UTF-8 BOM bytes 0xEF, 0xBB, 0xBF (ensures ₹ rupee symbol opens cleanly in Excel).
  • Only contains flagged invoices (needs_review and exception).
  • Text cells starting with =, +, -, or @ are prefixed with '.

🔒 Section 5: AI Anti-Hallucination Guardrails

The backend implements a strict multi-stage validation barrier before any AI-generated explanation is returned or persisted:

Strict Anti-Hallucination Enforcements:
  1. Character & Sentence Limits: Maximum 3 sentences and ≤ 600 characters.
  2. Invoice ID Whitelisting: Every uppercase token matching [A-Z]{2,5}-\d{2,} must be present in the verified record's invoice_id or matched_record. Fabricated IDs (e.g. INV-9999) fail validation immediately.
  3. Rule ID Whitelisting: Every ID in referenced_rule_ids must exist in the record's triggered violations.
  4. Fallback Safety: If an LLM response fails validation twice, the system falls back to the deterministic rule-based template without crashing.
